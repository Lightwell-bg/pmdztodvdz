Дата прогона: 2026-10-08. Стенд: `docs/LOCAL_STAND.md` (WordPress 7.1.3, EDD 3.7.1.1, SQLite, PHP 8.5 32-bit, шлюз `manual`, тестовый режим).

## Проверено локально на тестовом шлюзе EDD (manual)

## Исправления, найденные при прогоне

- `src/Http/RestController.php`: «Ожидаем подтверждения оплаты» для брошенного `pending` больше не висит вечно (правило 30 минут, `RestController::isPendingReportable`, тесты `tests/Http/PendingReportTest.php`).
- `src/Commerce/ReceiptIntegration.php`: на странице подтверждения после оплаты (блок `edd/confirmation`) не срабатывал `edd_order_receipt_after_table`, кнопки «Открыть инструкцию» не было. Добавлен хук `edd_order_receipt_order_details` и защита от двойного вывода на странице квитанции.

- НЕ проверено: Stripe test mode (реальный платёж, 3-D Secure, возврат на страницу успеха с `payment_intent`).
- НЕ проверено: реальный webhook Stripe (подпись, порядок событий, повторная доставка). Завершение заказов через `wp eval` / `edd_update_order_status` - **не** проверка webhook.
- НЕ проверено: задержка подтверждения в Stripe (заказ `processing`/`pending` в момент возврата покупателя на страницу, опрос `/result`).
- НЕ проверено: возвраты и споры из Stripe Dashboard (частичный возврат Stripe без записи по позиции, `charge.dispute.created`).

## Особенности стенда

- В исходной установке не хватало таблиц EDD (`edd_sessions` и таблиц `*meta`), из-за чего корзина была пустой. Таблицы созданы вызовом `install()` классов `EDD\Database\Tables\*`; при пересоздании стенда повторить.
- `php -S` кэширует realpath 120 секунд: при имитации сбоя через переименование `autoload.php` сбой воспроизводится, только если с последнего рендера PDF прошло больше двух минут.
- Токен-ссылка многоразовая в пределах срока действия (открывается с нескольких устройств); каждая отправка письма квитанции выпускает новую запись grant.

## Проверка конкурентности на InnoDB

Скрипт `bin/concurrency-check.php` гоняет настоящие `SlotRepository` и `CreditRepository` на реальном MySQL/MariaDB (InnoDB) с несколькими независимыми соединениями и 8 параллельными процессами PHP. Он создаёт свои таблицы `{prefix}units|seats|credits` (по умолчанию префикс `bgdvzh_cc_`, префикс обязан содержать `cc`), в конце удаляет только их. Нужен php с `pdo_mysql`; базу берите отдельную (локальную или staging), не боевую.

Сценарии: a) один слот, 8 процессов; b) перекрытие с перерывом; c) последнее письменное место; d) один зачёт; e) поздняя оплата против занявшего время (200 итераций со случайным порядком); f) параллельный перенос в один слот; g) deadlock 1213, lock wait 1205 и путь повтора.

```bash
php bin/concurrency-check.php --dsn="mysql:host=127.0.0.1;port=3407;dbname=bgdvzh_test;charset=utf8mb4" --user=root --pass=root
# необязательно: --prefix=bgdvzh_cc_ --only=a,e --iterations=200 --workers=8
```

Код выхода 0 — все PASS. Через PHPUnit (без переменной тесты пропускаются, обычный набор зелёный без MySQL):

```bash
BGDVZH_TEST_MYSQL_DSN="mysql:host=127.0.0.1;port=3407;dbname=bgdvzh_test;charset=utf8mb4" BGDVZH_TEST_MYSQL_USER=root BGDVZH_TEST_MYSQL_PASS=root \
  php .tools/phpunit.phar -c phpunit.xml.dist tests/Concurrency
```

Лог ошибок рабочих процессов: `bgdvzh-cc-worker-N.log` во временной папке системы.
